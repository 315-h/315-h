ENGINEERING METHOD

模型之外的那一层

三款 AI 产品都走过「从 0 到 1 搭功能」，接下来要解决的是「从 1 到 N 保稳定」。这一层不写在提示词里，写在代码里：约束、兜底、trace、评测，以及最关键的一步——评测结果回写成约束。

01 / Definition

先把这一层叫什么说清楚

2026 年 2 月 Mitchell Hashimoto 提出 Harness Engineering，LangChain 给了一个最简的拆法。它不是新框架，也不是模型微调——它是模型权重之外、决定系统能不能稳定交付的全部工程层。

Agent = Model + Harness

Harness = Agent − Model。把模型拿掉之后剩下的东西，就是这一层。

约束 → 执行 → 观测 → 评测 → 回写

八层不是功能清单，是一个闭环。跑完评测没有回写成约束，只能叫半套。

#层它回答的问题在三款产品里的具体形态
1约束什么绝对不能做输出 Schema 校验、阈值配置、状态转移表
2编排多步任务怎么串13 节点状态图／手写函数编排／四 Agent 串行
3记忆跨轮次记住什么会话状态、全局记忆（底线／偏好／历史）
4检索给模型看什么材料向量 + 关键词 + 合并 + 二次检索；轻量关键词召回
5工具能对世界做什么动作数据库与对象存储、抉择存档、文件导出

8评测怎么知道变好了分层测试集、分支断言、三档口径、基线对比

03 / Breakpoints

三个项目，断在闭环的不同位置

真正的缺口不是「没有 harness」，而是闭环断在不同环节。所以推进顺序不是按项目平均用力，是按断点从最薄处补。

小办闭环走到 ④，没回到 ①

评测台能出报告、能做基线对比，但报告出来之后没有「据此改约束」的动作——跑完就存档。这是三个断点里最薄的一处，也是本轮投入最重的地方。

本轮已闭合：R1–R36 回写记录＋6 个生产缺陷修复
经历翻译官闭环只走到 ②

执行层有编排、有检索、有兜底，但出场没有记录，也没有测试集。护栏是三个项目里最标准的，却没有任何数据能证明它有效。要先补观测，再补评测。

待补：结构化重试 + 逐条 trace + 报告评测集
缓择星球闭环的起点建错了地方

架构文档里反复强调「绝不越权、绝不串岗、禁止循环」，但全是提示词里的祈使句，代码层没有拦截非法转移的转移表。约束随时可能被模型忽略。要先补约束。

待补：转移表代码化 + 四 Agent 输出 Schema
04 / Evidence

已落地的那一部分：小办评测台

这是三个项目里唯一成型的 harness 组件，也是后续两个项目的参照样板。它的价值不在「跑出了一个分数」，而在下面这张表——它证明了旧口径的分数是假的。

断言有效性实测：注入分支漂移之后

把 118 条用例的分支期望逐条断言之后，人为注入分支漂移，对比三种口径的反应。

跨模型回归：哪些结论稳、哪些不稳

  • 逐格相同：换生成厂商后，终端分支分布完全一致（正常 106 / 兜底 11 / 冲突 1），全命中与宽松口径逐位相同，生产缺陷均为 0。
  • 有波动但不作结论：50% 口径差 2.5pt，逐例看全是答案用词层面的变化，且 7 条路由漂移全部落在「直答 ↔ 检索」之间，属采样噪声。
  • 判读铁律：离散量（分支分布、字段是否写入）给强结论；文本类指标给弱结论。

13 个生产节点在换厂商时一行代码未改即可跑通，说明 JSON 契约层是厂商中立的。

两个判官：关键词漏掉的，语义抓住了

  • 行为型要求用逐字关键词判天生脆弱：同一合规语义实测出现 5 种措辞，扩词追不上。因此接入第二个判官做语义判定，不替换主判定，只作为并行第二口径。
  • 验证方式含阴性对照：标注全反转后一致率从 45/45 掉到 0/45，证明判官真的在读回答，而不是在猜标注方向。
  • 第一例真实分歧：「必须转人工」这条要求被关键词按一半权重静默放过，语义判官判失败；换成另一家模型后，同样的问题两轮独立复现。

跨厂商判官偏差实测 +0.0pt，但样本只有 8 个组合，只能说「未观察到」，不足以排除更小的偏差。

05 / Principles

做多少就够了：四条判断准则

这一层不是越多越好。每一层都要跟着业务改，三个项目各搞一套等于同时维护三个小框架。所以先定边界，再动手。

01按「错一次的代价」分层
错了要担责或违规的环节重投入，只是体验差一点的环节抽检即可。制度冲突答错会误导报销，必须硬约束；一段文案的风格不够好看，抽查就够。
02先闭环，后加层
一条最薄的完整闭环（trace → 评测 → 回写），胜过八层里各做一点。三个项目都是「层数不少、闭环不全」，先补断点，别急着加层。
03能写进代码的，不写提示词
提示词约束是概率性的，代码约束是确定的。把「绝不越权」落成转移表，把拍的阈值放进配置文件并附数据依据，而不是继续加感叹号。
04每一层都要能单层开关
出问题时要能降级回退。评测台支持关闭重试、切换运行模式、限定用例范围；阈值配置写坏时一律回落代码默认值，行为与改动前完全一致。

明确不做

这些是平台级团队才需要的基础设施。三个项目合计的用户量、团队规模与迭代频率都不到那个量级，做了只会是维护负债。

  • 分布式链路追踪（OTel / Jaeger）
  • 在线 A/B 实验平台
  • 自动化 CI 门禁
  • 向量库选型对比
  • 多租户与权限体系
  • 自建 LLM 网关
  • 全量提示词版本管理平台

一句话标准：必备的四件（Schema 校验加重试、兜底路径可测、一份能跑的评测集、一次 trace 落盘）全部到位，就已经超过多数 AI 产品的工程水位。

06 / Boundaries

哪些不该套这一层，以及它现在还不能证明什么

引入之前先划边界，是为了防止后面越做越重。判断准则只有一个问题：这个环节错一次的代价，是否大于维护它的成本。

不适用单次性、一次性任务
运行一次就结束，没有回归需求，评测是纯浪费。作品集的 PDF 生成脚本就属于这一类。
不适用纯静态展示页面
没有模型参与，不存在概率性输出，也就没有可评测的对象。
不适用还在探索产品形态的阶段
需求每周都变，评测集会跟着重写，维护成本远高于收益。要等输入分布稳定下来再建。
不适用没有稳定输入分布的环节
评测集需要代表性样本。不知道用户会问什么的时候，测出来的数字没有参考意义。

口径声明（必须说，不等追问）

  • 绝对分不能替换简历数字。这套评测用的是替代语料（原始知识库文档本地不可得）与另一家模型，与线上归档结果属于不同运行时、不同判定器下的两个数，不能互换，也不能说「复现为 X%」。
  • 它只用于结构性诊断。能得出结论的是「某条路径是不是死代码」「某个字段有没有被写入」这类结构问题；不能用于评判线上模型能力。
  • 「评测台已建成并可运行」不等于「已产出可外推的质量结论」。这两件事在面试里必须分开说。

已知局限

  • 自评偏差未彻底消除。语义判官与被测系统同厂商，靠窄任务、强制引用原文证据、跨厂商交叉验证来压制，但只能说「未观察到」，不能说「已消除」。
  • 标注集是单方判定，不是人工双标。一致率 100% 只代表与我的判断一致，不代表与共识一致。
  • 偏差实验样本偏小，8 个组合不足以排除更小的偏差；跨模型轮次只跑了一次，没有重复测量。
  • 评测集本身需要 lint。已经查出两条「期望词包含禁止词」的矛盾用例——无论系统多好都不可能通过。有评测不等于测对了，跑得越勤可能错得越自信。
